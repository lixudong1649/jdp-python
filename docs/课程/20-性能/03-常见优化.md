# 20.3 常见优化

> 前置：20.1 timeit、20.2 复杂度 · 约 35 分钟 · 官方对应：[Python 性能提示 FAQ](https://docs.python.org/zh-cn/3/faq/programming.html#what-is-the-most-efficient-way-to-concatenate-many-strings-in-python) · 核对日期 2026-10-18

## 目标

- 掌握字符串拼接用 `''.join` 而非大规模 `+=`。
- 知道 **局部变量** 比反复属性查找稍快，但仅在热点路径值得做。
- 区分算法优化、数据结构优化与微优化；遵循「测量 → 改热点 → 再测量」。
- 能把 `slow_math` 的公式优化与字符串/join 优化放在同一决策框架里。

## 核心概念

### 字符串拼接：join 胜循环 +=

CPython 对 `s += part` 多次会创建中间字符串对象；大批量应收集到 list 再一次 `join`。

```python run
import timeit

n = 800
parts = [f"item-{i}" for i in range(n)]

def join_way() -> str:
    return "".join(parts)

def plus_way() -> str:
    out = ""
    for p in parts:
        out += p
    return out

t_join = timeit.timeit(join_way, number=200)
t_plus = timeit.timeit(plus_way, number=200)
print("片段数", n)
print("join 总秒", round(t_join, 4))
print("+= 总秒", round(t_plus, 4))
print("+=/join 比值≈", round(t_plus / max(t_join, 1e-12), 1))
```

大批量拼接时 `+=` 反复分配中间字符串，总耗时通常明显高于一次 `join`。输出打印比值而非绝对秒数，便于在不同 Pyodide 环境里仍看出 **join 是热点路径上的首选**。

### 局部变量绑定热点名称

在紧密循环里，把 `self.method` 或 `math.sqrt` 绑到局部变量可减少查找：

```python run
import math

def sum_roots(n: int) -> float:
    sqrt = math.sqrt
    total = 0.0
    for i in range(1, n + 1):
        total += sqrt(i)
    return total

print(0 < sum_roots(50) < 500)
```

差异通常很小；只有 cProfile 显示该循环占主导时才值得写丑一点。

### 算法优先：回到 slow_math

```python run
import timeit

def sum_squares_loop(n: int) -> int:
    total = 0
    for i in range(n):
        total += i * i
    return total

def sum_squares_local(n: int) -> int:
    rng = range
    total = 0
    for i in rng(n):
        total += i * i
    return total

def sum_squares_formula(n: int) -> int:
    return n * (n - 1) * (2 * n - 1) // 6

n = 2000
number = 300
t_loop = timeit.timeit(lambda: sum_squares_loop(n), number=number)
t_local = timeit.timeit(lambda: sum_squares_local(n), number=number)
t_formula = timeit.timeit(lambda: sum_squares_formula(n), number=number)
print("n=", n, "number=", number)
print("普通循环", round(t_loop, 4), "局部绑定", round(t_local, 4))
print("公式", round(t_formula, 6))
print("公式 vs 循环 倍数≈", round(t_loop / max(t_formula, 1e-12), 0))
```

20.3 强调 **微优化（局部绑定 range）相对普通循环往往只有小幅差异**，而 O(1) 公式相对循环是数量级差距。与 20.2 的「多 n 等价性」演示互补，此处用 timeit 量化优先级：先换算法，再谈局部变量。

### 生成器与惰性

不需要完整列表时，用生成器表达式省内存（不总是更快，但降峰值内存）：

```python run
def count_positive_list(data: list[int]) -> int:
    return sum(1 for x in data if x > 0)

def count_positive_gen(data: list[int]) -> int:
    return sum(1 for x in (x for x in data if x > 0))

sample = [1, -1, 2, 0, 3, 4, -2]
as_list = count_positive_list(sample)
as_gen = count_positive_gen(sample)
print("样本", sample)
print("生成器过滤计数", as_list)
print("嵌套生成器计数", as_gen)
print("结果一致", as_list == as_gen)
print("不必 materialize 全表", "惰性过滤省峰值内存")
```

两种写法对同一列表给出相同计数，说明 **过滤 + 累加可用生成器惰性完成**。当数据流很大时，避免先建完整中间 list 可降低峰值内存；是否更快仍要用 timeit 在真实规模上测量。

## 易错点

- **过早优化**：功能未稳、测试未覆盖就调 join/局部变量。
- **牺牲可读性换纳秒级**：团队维护成本更高。
- **在非热点路径 copy 大列表**：`list(big)` 本身昂贵；用迭代或切片视图思维。
- **未计入 I/O**：字符串拼接再快，网络仍是瓶颈（见 18–19）。

错误拼接方式在逻辑上仍可能「看起来对」，但复杂度差：

```python run
parts = ["a", "b", "c"]
bad = ""
for p in parts:
    bad += p
good = "".join(parts)
assert bad == good
print(len(good) == 3)
```

## 读代码

`sum_squares_fast` 注释中的公式即 **数学化简**，属于最高杠杆优化：

```python fragment
def sum_squares_fast(n: int) -> int:
    # n*(n-1)*(2n-1)//6
    return n * (n - 1) * (2 * n - 1) // 6
```

- 注释帮助读者对照数学推导，防止照抄公式却不理解边界（`n=0` 仍得 0）。
- 若把 `// 6` 写成 `/ 6` 再 `int()`，大数浮点可能丢精度；整数运算保持精确。
- 与 `downloader.py` 对比：I/O 并发优化网络等待；`slow_math` 优化 CPU 路径——**瓶颈不同，手段不同**。

`test_slow_math.py` 防止优化破坏正确性，是发布前的门禁。

当你准备把 `sum_squares_fast` 换成 `functools.cache` 装饰的递归版本时，先问：缓存是否比 O(1) 公式更简单、是否引入内存上限？多数情况下公式仍胜出——**选最简的正确算法**，再考虑 cache 与并行。

拼 SQL 或 shell 命令字符串时，同样适用 `join` 思维：用固定分隔符连接已转义片段，而不是在循环里盲目 `+=` 用户输入——这既是性能问题，更是安全问题（注入）。

**优化优先级（建议顺序）**：

1. 正确性与测试（`test_slow_math` 一类）。
2. 算法与数据结构阶次（`sum_squares_fast`）。
3. 减少 I/O 次数与 payload 体积。
4. 并发模型（18–19 章）。
5. 微优化（`join`、局部变量、内置函数）。

跳步往往导致在错误热点上浪费时间。

完成阶段 20 后，建议对 `sum_squares_slow` 跑一次 20.1 的 `timeit` 对比，把数字写进学习笔记——亲手测一次比只看公式更有体感。

阶段 18–20 形成闭环：并发重叠等待、async 重叠 I/O、测量与算法优化——按瓶颈类型选用，而不是堆叠所有技巧。

`io.StringIO` 适合在内存中拼接超大文本后再一次性写出文件；比无限 `+=` 更可控，但仍不如分块写盘节省内存。

列表推导往往比手动 `append` 循环稍快且更易读，但超大序列仍要考虑生成器以省内存。

完成本阶段后，用同一组 `n` 对 `slow_math` 跑通 20.1 的测量脚本，作为阶段 20 综合小实验。

若优化后测试仍绿但用户感知仍慢，瓶颈可能在网络或数据库；回到 18–19 与外部监控数据。

`functools.cache` 适合纯函数重复调用；有副作用或可变参数的函数不应盲目缓存。

读 CPython 源码时，留意热点 C 函数；那通常比改 Python 微语法更有效。

性能优化文档应链接到基准测试命令，方便复查。

`slow_math` 项目证明：有时一行公式胜过百行微优化技巧。

把本课 join 与局部变量技巧记在速查卡上，但执行顺序永远是：正确性 → 算法 → I/O → 微优化。

阶段 20 至此收束 M3 性能与并发叙事主线。

## 练习

### 练习 1：join 拼接

实现 `concat_words(words: list[str]) -> str`：无分隔符拼接；`[]` 返回 `""`。

```python exercise id=s20-l03-opt
# --- starter ---
def concat_words(words: list[str]) -> str:
    return "x"
# --- solution ---
def concat_words(words: list[str]) -> str:
    return "".join(words)
# --- check ---
assert concat_words(["a", "b"]) == "ab"
assert concat_words([]) == ""
```

### 练习 2：过滤正数求和

实现 `sum_positive(nums: list[int]) -> int`：只累加严格大于 0 的元素。

```python exercise id=s20-l03-pos
# --- starter ---
def sum_positive(nums: list[int]) -> int:
    return 0
# --- solution ---
def sum_positive(nums: list[int]) -> int:
    total = 0
    for x in nums:
        if x > 0:
            total += x
    return total
# --- check ---
assert sum_positive([1, -2, 3, 0]) == 4
assert sum_positive([]) == 0
assert sum_positive([-1]) == 0
```


## 小结

- 大批量字符串用 `join`；循环热点可考虑局部绑定，但先 profile。
- 算法与数据结构优先于微优化；`slow_math` 是标准范例。
- I/O 与 CPU 瓶颈用不同手段（async/线程/公式），别混为一谈。
- 每次优化后用测试与 timeit 验证正确性与收益。
- `join` 是字符串批处理的首选惯用法。
- 微优化只应在 profile 热点上考虑。
- 字符串、循环、算法三层优化不要颠倒顺序。
- 阶段 18 并发与阶段 20 测量应结合使用。
- 发布前对关键路径跑一次 profile 是低成本保险。
- 优化 PR 应附带测试，防止回归。
