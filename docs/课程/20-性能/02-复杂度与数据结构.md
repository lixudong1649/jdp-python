# 20.2 复杂度与数据结构

## 目标

- 用大 O 直觉比较 `list`、`set`、`dict` 的常见操作成本。
- 避免「嵌套循环 + list 成员检测」导致的 O(n²) 爆炸。
- 会把 Agent 工具表、注册表设计成 **dict 查找** 而非线性扫描。
- 结合 `slow_math` 理解：算法阶次往往比微优化更重要。

## 核心概念

### 成员检测：list vs set

`x in items` 对 list 是 O(n)，对 set/dict 键平均 O(1)。

```python run
items_list = list(range(5000))
items_set = set(items_list)
target = 4999
print(target in items_list, target in items_set)
```

当循环里反复 `if x in big_list`，应先把 `big_list` 转成 `set`。

### dict 作为注册表

工具名 → 可调用对象，查找一次完成：

```python run
def add(a: int, b: int) -> int:
    return a + b

def mul(a: int, b: int) -> int:
    return a * b

TOOL_FUNCTIONS = {"add": add, "mul": mul}

def dispatch(name: str, a: int, b: int) -> int:
    fn = TOOL_FUNCTIONS[name]
    return fn(a, b)

print(dispatch("add", 2, 3), dispatch("mul", 2, 3))
```

读 `minimal_agent` 时，`TOOL_FUNCTIONS[block.name]` 就是 O(1) 平均查找。

### 嵌套循环陷阱

对每个用户查每个组：

```python run
users = ["u1", "u2", "u3"]
groups = [["u1"], ["u2"], ["u3"]]

def belongs_naive(user: str) -> int:
    count = 0
    for g in groups:
        if user in g:
            count += 1
    return count

print(belongs_naive("u1"))
```

若 `groups` 很大且元素是 list，内层 `in` 又 O(n)。预处理 `user -> set(groups)` 或合并索引可降到 O(1) 查询。

### 与阶段 20 项目的联系

`sum_squares_slow` 是 O(n) 次加法；`sum_squares_fast` 是 O(1)。数据结构换不了阶次时，要换 **公式或算法**。

```python run
def sum_squares_slow(n: int) -> int:
    return sum(i * i for i in range(n))

def sum_squares_fast(n: int) -> int:
    return n * (n - 1) * (2 * n - 1) // 6

n = 200
print(sum_squares_slow(n) == sum_squares_fast(n))
```

## 易错点

- **频繁 `list.append` 再 `in list` 去重**：应直接用 `set` 或 `dict.fromkeys`。
- **把 O(n) 当成「够快」**：数据量翻倍两次就可能从毫秒变秒级，先用复杂度估算再写代码。
- **用 list 当下标映射**：稀疏键应用 `dict`。
- **sorted 全表再 bisect**：若只需最大值，遍历或 heap 更合适。
- **只看常数项、不看阶次**：n=10 时 O(n²) 无所谓；n=10⁶ 时致命。

对空 list 做成员检测不会抛错，但逻辑可能错：

```python run raises=AssertionError
allowed = []
assert 0 in allowed, "空列表不应包含任何业务键"
```

## 对照

| 操作 | list | set | dict |
|---|---|---|---|
| 按下标访问 | O(1) | — | O(1) 键 |
| 尾部 append | 均摊 O(1) | — | — |
| `x in` | O(n) | O(1) 平均 | O(1) 键 |
| 排序 | O(n log n) | — | — |
| JS 近似 | Array | Set | Map |
| Java 近似 | ArrayList | HashSet | HashMap |

## 读代码

`test_slow_math.py` 用多个 `n` 验证快慢实现 **等价**，这是性能优化前的安全网：

```python fragment
def test_equivalent() -> None:
    for n in (0, 1, 10, 100):
        assert sum_squares_slow(n) == sum_squares_fast(n)
```

- 覆盖 `n=0` 边界，防止公式在空范围出错。
- 先正确性、再 timeit；否则快而错无意义。
- 与工具注册表一样：**先保证 dispatch 正确**，再谈缓存或并行。

`downloader.py` 用 `list` 存 URL 顺序合理（n 小）；若 URL 去重应用 `dict.fromkeys(urls)` 保序。

面试与代码审查里常问「若 URL 上亿条怎么办」：此时不应在内存里持完整 list，而应流式读入、分批 `submit`，并用 `set` 做已见去重；复杂度分析要先问数据是否必须全在内存。

`collections.deque` 在两端插入是 O(1)，适合滑动窗口；`list.pop(0)` 是 O(n)。读性能相关博客时，若作者用 list 当队列，应警惕 hidden quadratic cost。

**常见操作复杂度速查（平均情况）**：

- `dict[k]` / `set` 成员：O(1)。
- `list.append`：均摊 O(1)；`list.pop(0)`：O(n)。
- `list.sort`：O(n log n)。
- 双重 for 扫两张表：O(n·m)。

把速查表写进团队 wiki，比每次凭感觉争论更能节省时间。

复习阶段 4 容器课时，把 `list`/`dict`/`set` 的操作复杂度与本课表格合并成一页笔记，后续读代码时随手查阅。

`in` 运算符对 `dict` 默认检查键而非值——复杂度按键空间计算，这是许多新手误用 `if user in users_dict` 时的根源。

两列表求交集时，`set(a) & set(b)` 通常优于双重循环；若需保序，可在交集后再按 `a` 的顺序过滤。

哈希表依赖 `__hash__` 与 `__eq__`；自定义类作 `dict` 键前须保证不可变语义（见阶段 12）。

下一课 20.3 讨论在热点路径上的字符串与微优化，但仍以本课阶次分析为前提。

写循环时先在纸上写下内外层规模 `n`、`m`，再估算是否为 O(n·m)；许多线上事故源于此处估算缺失。

当 `n` 从 1e4 涨到 1e6 时，O(n) 与 O(n²) 的差距会从「感觉不到」变成「服务不可用」。

审查他人 PR 时，看到嵌套循环先问数据规模，再问是否可换 `dict`/`set` 索引。

### 练习 1：用 set 去重保序思路

实现 `unique_sorted(nums: list[int]) -> list[int]`：返回 **升序** 且无重复的元素列表（可用 `sorted(set(nums))`）。

```python exercise id=s20-l02-ds
# --- starter ---
def unique_sorted(nums: list[int]) -> list[int]:
    return nums
# --- solution ---
def unique_sorted(nums: list[int]) -> list[int]:
    return sorted(set(nums))
# --- check ---
assert unique_sorted([3, 1, 2, 2]) == [1, 2, 3]
assert unique_sorted([]) == []
```

### 练习 2：注册表查找

实现 `register(tools: dict, name: str, fn)`：把 `fn` 登记到 `tools[name]`；`lookup(tools, name)` 返回对应函数并调用无参得到值（测试用零参 lambda）。

```python exercise id=s20-l02-reg
# --- starter ---
def register(tools: dict, name: str, fn) -> None:
    pass

def lookup(tools: dict, name: str):
    return tools[name]
# --- solution ---
def register(tools: dict, name: str, fn) -> None:
    tools[name] = fn

def lookup(tools: dict, name: str):
    return tools[name]
# --- check ---
t = {}
register(t, "zero", lambda: 0)
assert lookup(t, "zero")() == 0
register(t, "one", lambda: 1)
assert lookup(t, "one")() == 1
```

## 小结

- 先选对容器：成员检测、注册表优先 set/dict。
- 警惕嵌套循环与 `in list` 组合成的 O(n²)。
- 算法阶次（slow vs fast）常比微优化更有效。
- 优化前后用测试保证等价，再用 timeit 量化收益。
- Agent 工具表用 `dict` 是 O(1) 查找的典型例子。
- 大数据场景先问能否流式处理，再问能否换容器。
- `deque` 与 `list` 混用是性能审查的常见检查点。
