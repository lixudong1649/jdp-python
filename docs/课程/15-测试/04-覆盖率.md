# 15.4 覆盖率概念

> 前置：15.1 pytest 基础 · 约 30 分钟 · 官方对应：[pytest 文档](https://docs.pytest.org/en/stable/) · 核对日期 2026-10-18

## 目标

- 把覆盖率当作**发现盲区**的信号，而不是团队 KPI 或绩效考核指标。
- 区分行覆盖与分支覆盖：100% 行覆盖仍可能没测对行为。
- 优先补**错误路径**与边界条件（空输入、非法参数、异常传播）。
- 知道本仓库如何用 `pytest --cov` 对阶段项目做本地检查（可选 dev 依赖）。

## 核心概念

### 覆盖率量什么

工具（常与 pytest 一起用的 coverage 插件）记录哪些源码行在测试运行中被执行过。示意：

```python run
def sign(x: int) -> int:
    if x > 0:
        return 1
    if x < 0:
        return -1
    return 0

def test_positive():
    assert sign(3) == 1

test_positive()
# 只跑 test_positive 时，sign 里 x<0 与 x==0 分支可能未执行
```

补用例后分支才完整：

```python run
def sign(x: int) -> int:
    if x > 0:
        return 1
    if x < 0:
        return -1
    return 0

assert sign(3) == 1
assert sign(-1) == -1
assert sign(0) == 0
print("branches touched")
```

### 错误路径值得单独写测试

```python run
def safe_div(a: float, b: float) -> float:
    if b == 0:
        raise ValueError("zero divisor")
    return a / b

try:
    safe_div(1, 0)
except ValueError as e:
    assert str(e) == "zero divisor"
else:
    raise AssertionError("expected ValueError")

assert safe_div(4, 2) == 2.0
```

`logstats.main` 当前未捕获 `FileNotFoundError`——若产品要求友好退出码，应加测试期望 `return 1` 并因此拉高分支覆盖。

### 本地命令（本仓库）

安装 dev 组后可以对子目录跑覆盖率（课内文档命令，不在浏览器执行）：

```bash
uv run pytest examples/项目/14-日志统计CLI --cov=examples/项目/14-日志统计CLI --cov-report=term-missing -q
```

阅读 `term-missing` 输出：左侧百分比，右侧 **Missing** 行号即未执行行。

### 覆盖率救不了的设计问题

| 现象 | 说明 |
|---|---|
| 全绿但 bug 仍在 | 断言太弱，只测了「没抛异常」 |
| 100% 行覆盖 | 可能没测输出内容、顺序、编码 |
| 为数字写无意义测试 | 调用函数但不 assert 行为 |

阶段 15 的 `test_parse_lines_ignores_lines_without_level` 表达的是**语义**：无级别行不计数，而不只是「跑过 parse_lines」。

### 与 CI 的关系

本仓库根目录在合并前通常跑全量 `pytest`；覆盖率可在本地按需加 `--cov`。CI 是否强制覆盖率由团队决定——课程只要求你能读懂报告、知道补哪类用例。

未覆盖行常见三类：防御性 `raise`、平台分支（Windows 专用）、以及你还没写的错误处理。第一类可保留；后两类要有意识地补测或标注原因。

对 CLI 项目，同时看「纯函数覆盖率」与「main 路径覆盖率」：前者快且稳定，后者保证 argparse 与文件编码没接错。

补测时优先复制真实 bug 报告里的输入：回归测试比盲目追百分比更能防止再犯。

阅读 HTML 覆盖率报告时，红色行是未执行，黄色常表示部分分支未走；不要只盯着顶部总百分比。

把覆盖率配置写在 `pyproject.toml` 或 `.coveragerc` 里，排除 `if TYPE_CHECKING:` 块与测试目录本身，避免数字被测试代码稀释。

多人协作时，在 PR 描述里贴一张 Missing 截图即可，不必争论个位数百分点；讨论焦点应是「这条路径用户会不会走到」。

若引入新依赖（如 HTTP 客户端），先写一条失败测试再实现，比事后补覆盖率更符合 TDD 节奏。

阶段 14 只有一条 `test_parse_lines`，15 阶段补的三条测试共同抬高了对 `parse_lines` 与 `main` 的信心——这就是渐进式补覆盖，而不是一次写满。

当重构删除死代码后，覆盖率会突然上升；此时应同步删除对应测试，避免测试维护已不存在的分支。

公开库维护者有时在 README 展示徽章；本课程项目不要求徽章，但应能在本地复现同样的 `pytest` 命令。

## 易错点

- **把覆盖率当发布门槛**：可以设团队下限（如 80%）作提醒，但应结合 code review。
- **排除过多 `# pragma: no cover`**：把复杂逻辑排除会让数字失真。
- **只测 happy path**：`parse_lines("")` 与「畸形行」往往比再多一条 INFO 用例更有价值。
- **混淆集成与单元**：覆盖率高可能全在集成测试；慢套件时仍应保留快单元测试。

```python run
def only_calls(fn):
    fn()  # 无 assert — 对覆盖率有用，对质量无用

def noop():
    return 42

only_calls(noop)
```

这类测试会执行代码但不验证结果，应禁止。

## 读代码

对 [`logstats.py`](../../../examples/项目/14-日志统计CLI/logstats.py) 做 mental coverage：

1. **`parse_lines`**：14 与 15 测试覆盖空串、含 INFO/ERROR、无级别行。若加 `WARNING`/`DEBUG` 样例，对应分支也会被执行。
2. **`main` 打印循环**：`test_main_on_sample` 走读文件 + 打印路径；若日志只有 ERROR，则 DEBUG/INFO 分支仍可能未打印——属于「未出现的级别」而非未覆盖行。
3. **`if __name__` 块**：通常不计入可测逻辑，或单独用集成测试启动脚本。

阶段 17 打包后模块名变为 `logstats_pkg.cli`，覆盖率命令要指向新包路径（17 课）。

团队评审时可以把 coverage 报告当「提问清单」：Missing 行是还没测到，还是死代码可以删？两者对策不同。

对异步与多线程代码，覆盖率数字更不可靠：同一行可能只部分等待；此时更应靠集成测试与类型检查（16.3）兜底。

```python exercise id=s15-l04-cov
# --- starter ---
def sign(x):

def sign(x):
    return (x > 0) - (x < 0)
# --- check ---
assert sign(3) == 1 and sign(-1) == -1
```

### 练习 2：`clamp`

实现 `clamp(x, lo, hi)`：若 `x < lo` 返回 `lo`，若 `x > hi` 返回 `hi`，否则 `x`。要求覆盖三条分支。

```python exercise id=s15-l04-clamp
# --- starter ---
def clamp(x: int, lo: int, hi: int) -> int:
    return x
# --- solution ---
def clamp(x: int, lo: int, hi: int) -> int:
    if x < lo:
        return lo
    if x > hi:
        return hi
    return x
# --- check ---
assert clamp(0, 1, 10) == 1
assert clamp(99, 1, 10) == 10
assert clamp(5, 1, 10) == 5
```

## 小结

发布前看一眼 Missing 列表即可，不必追求每周追逐 100%；把时间花在用户会碰到的失败模式上更有回报。

若某文件长期 0% 且是生成代码或薄封装，可以在评审里讨论是否移出统计范围，而不是机械补测。

- 覆盖率找「没跑到」的行；分支与异常路径优先补测。
- 高覆盖率 ≠ 高质量；断言必须描述期望行为。
- 本仓库用 `pytest --cov ... --cov-report=term-missing` 对照阶段项目。

- [pytest 文档](https://docs.pytest.org/en/stable/)
- [Python 打包项目测试章节](https://packaging.python.org/en/latest/tutorials/packaging-project/#creating-a-test)
- [如何编写断言（pytest）](https://docs.pytest.org/en/stable/how-to/assert.html)

覆盖率统计不包含课内 ` ```python run ` 块：那些由 `check_course.py` 执行，与 pytest 收集的 `examples/项目` 测试是两套管线。

因此阶段达标仍以 `pytest` 全绿为准，覆盖率只是额外仪表盘。

对比同事 PR 时，关注新增代码是否附带至少一条针对新分支的测试，而不是总百分比波动。

若 Missing 出现在 `except` 子句，问一句：这个异常用户能见吗？能就要测，不能就要么删掉要么换成更窄的异常类型。

`logstats.parse_lines` 的循环体在空文件时仍会执行一次 `splitlines` 逻辑——覆盖率和性能无关，但空输入测试能锁住「不抛异常」契约。

打印语句（`print`）不影响行覆盖统计方式，但若 main 将来改为 `logging`，记得同步调整测试里对输出的断言方式。

长期维护时，每隔几个阶段回顾一次 Missing 列表，比每次 PR 强制 100% 更可持续。

完成 15 阶段后，运行 `uv run pytest examples/项目/15-CLI测试 -q` 应看到 3 条用例全部通过。
