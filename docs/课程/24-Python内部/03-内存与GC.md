# 24.3 内存与 GC

> 前置：24.1 名字绑定 · 约 35 分钟 · 官方对应：[gc 模块](https://docs.python.org/zh-cn/3/library/gc.html) · 核对日期 2026-10-18

## 目标

- 理解 CPython **引用计数** 为主、**循环垃圾回收** 为辅的内存模型。
- 会用 `sys.getrefcount`（注意其额外 +1）观察引用变化，而非精确泄漏检测。
- 知道 **循环引用**（互相指向的容器）需 `gc` 收集；长生命周期 Agent 注意 `messages` 增长。
- 了解 `weakref` 场景：缓存但不阻止回收（本课点到为止）。
- 能区分引用计数归零与 `gc` 周期回收的时间差。

## 核心概念

### 引用计数直觉

```python run
import sys

a = []
print(sys.getrefcount(a) >= 2)  # 含 getrefcount 临时引用
b = a
print(sys.getrefcount(a) >= 3)
del b
```

### 循环引用

```python run
import gc

class Node:
    def __init__(self):
        self.peer = None

a = Node()
b = Node()
a.peer = b
b.peer = a
del a, b
print(gc.collect() >= 0)
```

### 小整数缓存（实现细节）

```python run
a = 256
b = 256
c = 257
d = 257
print(a is b)
print(c is d)  # 可能 False，取决于实现与作用域
```

### `__slots__` 减少 per-instance dict

```python run
class Plain:
    def __init__(self, x):
        self.x = x


class Slim:
    __slots__ = ("x",)

    def __init__(self, x):
        self.x = x

p = Plain(1)
s = Slim(2)
print(hasattr(p, "__dict__"), hasattr(s, "__dict__"))
```

### 显式触发 gc

```python run
import gc

gc.set_debug(0)
unreachable = gc.collect()
print(type(unreachable), unreachable >= 0)
```

## 易错点

- **把 `getrefcount` 当泄漏工具**：仅教学；生产用 `tracemalloc`、`objgraph`（第三方）等。
- **循环引用 + `__del__`**：历史上难回收；3.4+ 改进了部分语义，仍应避免在 `__del__` 里做重逻辑。
- **长列表不释放**：Agent `messages` 无限增长是“逻辑泄漏”，不是 gc 问题，要截断或摘要历史。
- **误以为 `del` 立即回收**：只减引用；对象可能仍被别处引用。

```python run
import weakref

class Big:
    pass

obj = Big()
w = weakref.ref(obj)
print(w() is obj)
del obj
print(w() is None)
```

| 机制 | CPython | JavaScript (V8) | Java JVM |
|---|---|---|---|
| 主要策略 | 引用计数 + 循环 gc | 分代 gc | 分代 gc |
| 循环结构 | `gc` 模块 | 引擎处理 | 可达性分析 |
| 弱引用 | `weakref` | `WeakMap` | `WeakReference` |

## 读代码

`minimal_agent.py` 的 `messages` 在循环中持续增长，每轮 append assistant 与 tool 结果：

```python
messages = [{"role": "user", "content": "上海今天天气怎么样？"}]

for turn in range(1, MAX_TURNS + 1):
    resp = client.messages.create(
        model=model,
        max_tokens=1024,
        tools=tools,
        messages=messages,
    )
    messages.append({"role": "assistant", "content": resp.content})
```

内存视角：

1. 每个 `append` 增加 list 长度，**峰值内存与轮数线性相关**。
2. `MAX_TURNS` 是硬上限，防止无限循环也限制历史长度。
3. 若把完整 `resp` 对象塞进历史而非精简 dict，会多占引用。
4. 会话结束后 `messages` 随栈帧结束可被回收，除非挂到全局。
5. 生产 Agent 常用“滑动窗口”或摘要压缩，而不是依赖 gc。

`mini_agent.REGISTRY` 持有函数对象，生命周期与模块相同，一般不构成循环引用；但若工具闭包捕获大对象，会延长其存活时间。

### 练习 2：限制历史长度

```python exercise id=s24-l03-trim
# --- starter ---
def trim(history: list[int], max_len: int) -> list[int]:
    return history
# --- solution ---
def trim(history: list[int], max_len: int) -> list[int]:
    if len(history) <= max_len:
        return history
    return history[-max_len:]
# --- check ---
assert trim([1, 2, 3, 4], 2) == [3, 4]
```

## 小结

- CPython 以引用计数为主；容器循环依赖 `gc.collect` 周期。
- Agent 长会话要管 **messages 逻辑增长**，不是等 gc 救场。
- `__slots__` 可减内存 footprint；热点数据结构才值得用。
- 弱引用适合缓存场景，不阻止对象被回收。
- 分代 gc 降低全堆扫描成本，对多数应用透明。
- `gc.disable()` 仅特殊基准场景，别在生产关闭。
- 大字节对象有专门分配器，与小块对象路径不同。
- 内存泄漏排查先看全局列表、缓存 dict、未关闭文件句柄。
- free-threaded 3.14+ 内存模型更复杂，本课以 3.12 默认 GIL 为准。
- 对象 `__sizeof__` 可粗估占用，非精确堆分配。
-  intern 字符串减重复存储，实现细节勿依赖。
- 长驻进程注意关闭文件与 socket，释放非 gc 资源。
- 核对日期 2026-10-18：3.12 默认带 GIL，free-threaded 构建另论。
- `gc.get_stats()` 可看各代回收次数，调优前先有基准。
- 避免在 `__del__` 里 import 模块，可能触发半初始化状态。
- 容器类实现 `__slots__` 前评估是否破坏子类 `__dict__` 需求。
- Agent 会话结束可将 `messages.clear()` 并 `gc.collect()` 仅作实验，生产靠截断策略。
